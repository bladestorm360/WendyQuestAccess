Reject address guesses, debugger dependence, existing DLL conflicts, and modifications to native Chromium sandbox behavior. No proxy was built or loaded.

### Map entry ordering for the first field checkpoint

- `SceneManager.goto` constructs the next scene before calling the outgoing scene's `stop`. `changeScene` later terminates the outgoing scene and calls the new scene's `create`. A close in `stop`, `terminate` or `onSceneTerminate` would miss the constructor boundary. Trace callers of `goto` and `push` before adding field admission. The current front end already uses accepted actions for its save, retry and title paths.
- `Scene_Map.create` starts the map read and clears image/effect caches for a transfer. `isReady` eventually runs `onMapLoaded`, which performs the transfer and creates display objects. `MapScene.start` calls `doSceneStart` after the transfer or fade-in handling. The latter calls `Game_Event.onSceneStart` for every event. That callback replaces native update delegates and restores custom data, including animation state for applicable events. `MapScene.update` then runs native update delegates before message handling and the main game update. A renderer stage or map ID observed on its own misses that first update and any startup interpreter work.
- On a transfer that requests autosave, stock `onTransferEnd` runs before `doSceneStart`. `MonkeyWrenchMZ.executeAutosave` uses the last loaded slot and has separate success and failure callbacks. The installed save pipeline fixture records the slot write, native saved-status animation entry, and then the detached global metadata write. Failure reaches the native failure callback without starting the metadata write. The file sink is inert. A drained event-loop turn in the fixture proves the scheduled work completed there. The actual renderer frame and any Steam Cloud work still need separate qualification.
- `Game_Map.setupStartingEvent` can start a reserved common event, a test event, a starting map event or an autorun. `Game_Event.start` marks an accepted event before the main interpreter picks it up. The interpreter requests its face and picture assets inside `setup`. Native bitmap completion can arrive later. The loader distinguishes a ready cache hit from work still loading. [Cached portrait evidence](navigation.md#cached-portrait-requests-and-the-all-category) In the fixture, movement is blocked both while the main event is queued and while the interpreter owns it. Scripted and random battles call `BattleManager.setup` before the battle scene is pushed. Scene replacement alone misses these earlier native entry boundaries.
- `MapScene.updateMoveDetector` publishes the game's result in `_prevCanMove`. The start map from `System.json` is map 038, which runs opening dialogue and transfer logic through parallel event 1. The fixture selects its second page through the installed page predicates with self switch A set. The parallel interpreter is running and has preloaded a face while the main event check is clear and `_prevCanMove` is true. The detector turns false once a message is busy. Field access must account for authored startup and reset contexts. Applying a blanket ban to all parallel events would also remove normal field access in areas that use them for puzzle state.
- The map banner's custom `Window_MapName.refresh` runs its text draw in an artwork callback. Stock `Window_MapName.update` applies a separate contents fade. The fixture sees text draw at zero opacity before the first fade-in update. Any speech for this banner needs both the original draw and current presentation evidence.

- The idle sequence starts with artwork loaded by `Scene_Map.updateInactive`. At 30 units of the game's inactivity clock, it can request a balloon and sound. Later thresholds hide the HUD, stop normal scene-change processing and create the overlay textures. The tested banner closes before that first timed cue and waits through pending idle artwork. A broader field observer still needs proof of wake behavior for navigation and input ownership.
- Map 038 and the secret-cave reset map 198 have empty native display names. The actual secret-cave room 196 has a native banner. A visible-banner observer can distinguish these without a map-ID exception. Of the installed 239 maps, 49 have a banner name. The longest is 25 UTF-16 code units, within the observer's 256-unit cap. Future navigation admission cannot infer playable state from this rule because legitimately playable maps can also omit a banner.

Run `tests/map-lifecycle.test.cjs` with Node and the installed root inside the bounded runner. It loads stock methods and decodes selected `MapScene`, `MonkeyWrenchMZ` and `CanvasScaler` methods into memory, with the same source-checked notification transforms used for the candidate. `tools/registration.py` pins the modified inputs. The stock `rmmz_windows.js` used for the window fixture hashes to `7bd37af5d4d55d2aedad4d2cb1e14d2ff3ff8eefa261f865ef805b7e8981fd59`. Actual map data supplies the Salt Caverns event, opening parallel event, reset room and secret cave. Assets, save writes, Steam callbacks and event command execution are stand-ins. ## Offline checks completed and reproducible procedure

1. Read the Steam manifest; inspect `package.nw` as a directory; hash the build identity files; parse PE import, delay import and export tables using the existing `pefile` package in fast-load mode. No binary was executed.
2. Read map, tileset, event and registry JSON directly. Confirm the map IDs exactly equal non-null `MapInfos` IDs, every grid has width × height × six entries, all event coordinates are in bounds, and all map tileset IDs resolve. Results: 239 maps, 191,235 map cells, 4,636 event instances, 6,527 pages, 51,215 map-page command rows, 250 common events, 175 troops and 17 tilesets. Largest grid: map 87 at 120 × 80. Largest event count: 244 on map 41. Static direct transfers alone reached 189 map IDs from the start with every conditional branch admitted; this is a graph sanity check and proves neither actual reachability nor exclusion of the other 50 maps.
3. Trace the linked interpreter commands by `(map ID, event ID, page)`, including common event calls and custom command names. Avoid executing event scripts in analysis. Inspect scripts on the existing install and decode the static literal tables without executing their plugin bodies.
4. In an isolated Node `vm` with a mock DOM, load only the installed stock `PluginManager.setup`, `setParameters`, `loadScript`, `makeUrl`, and `onError` methods. Supply the locally parsed registry plus one synthetic marker. Verified order and script URLs for all 24 descriptors and that repeating setup did not append duplicates. DOM execution and the actual NW.js launch sequence were not exercised.
5. In the same fixture load the stock `Game_Map.checkPassage`, `tileId`, `layeredTiles`, `allTiles`, `isPassable` and `Game_Event.findProperPageIndex`/`meetsConditions` methods. Use Salt Caverns' real dimensions and tileset, stub tile events as empty and supply the real crystal event with mock switch state. All 14,000 direction/tile cases completed: 11,319 pass and 2,681 block in base geometry. Setting the crystal's D self switch selects page 2 over page 1. This is base engine evidence; custom overrides, dynamic blockers, event occupancy and puzzle progression are deliberately unmodeled.

The map/script audits and Node fixture used the canonical machine-wide job runner with 128 or 256 MB aggregate caps and one worker. These were functional offline checks. No native/runtime responsiveness, hook overhead, speech latency, installed behavior, or accessibility was measured. No game, save, plugin, network reward or Steam API was run.
