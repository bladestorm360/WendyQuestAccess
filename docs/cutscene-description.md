# Audio description for cutscenes

The game can stage a visible action between voiced dialogue pages. The suggested scope is a short line only when that action adds information the dialogue does not state. Author the line once, attach it to the native event beat, and let the player hear it at ordinary narration speed. Keep it independent of NVDA and use the game audio mix or a separate speech output with adjustable speed and volume. Automatic scene description would be optional.

## First verified scene

Crispy Ruins, Map 016, event 36, first page, stages the capture after the battle. At commands 22–24 the game plays the mech sounds and changes the scene switch. At commands 25, 41 and 57 both mechs and Elder Tater start matching upward movement routes. The command at 57 waits for the Elder's movement to complete. The subsequent line conveys his scream, and the next Wendy dialogue acknowledges the need to continue. The actual lifting and departure are communicated by the animation and sound. A candidate sentence for the visible movement is “The two mechs rise into the air, carrying Elder Tater away.”

Use the native scene identity and an authored checkpoint after the motion first reaches a rendered frame. The two mechs can start moving before the elder's route executes. The narration must follow the visual change, survive ordinary dialogue playback in a separate voice, and retire with the current scene if the user advances or the game transfers. Avoid a generic move-route observer or a new game-thread wait. Audit other visual-only beats first and keep lines short enough for the available gaps. Verify each chosen beat with the installed event data and offline tests before claiming coverage.

## Voice options for discussion

| Option | Added mod download | Behavior |
| --- | --- | --- |
| Short compressed clips | At 24–48 kbps mono, 180–360 KB per minute in decimal units, before modest packaging overhead. Three to five minutes add roughly 0.5–1.8 MB. | Predictable delivery and no inference or text sent to a service during play. A narrator or AI can record the prewritten lines once. Playback gain and pitch-preserving playback speed can be adjusted separately. Actual quality, compressed size and rate changes need a sample. |
| Windows voice | No model in the mod. | Read the same text through Windows synthesis and route it to the audio device independently of NVDA. The installed API-visible English voices are David, Mark and Zira through the available voice registrations. The standard speech synthesis API can enumerate installed supported voices. No proof that Narrator's Natural voices are accessible through this path on this machine. [Microsoft SpeechSynthesizer](https://learn.microsoft.com/en-us/uwp/api/windows.media.speechsynthesis.speechsynthesizer) |
| Optional neural voice | No model in the main mod when the model and runtime are separately installed. The example Lessac Medium model is 63.2 MB by itself. | Generate audio from prewritten text on demand, locally. Extra setup, runtime memory and cold-start latency warrant a bounded proof before connecting it to cutscenes. [Piper Lessac model](https://huggingface.co/rhasspy/piper-voices/tree/441d4acfc479677c7f0ea54f722b39ad58f3fb70/en/en_US/lessac/medium) · [sherpa-onnx speed and playback example](https://github.com/k2-fsa/sherpa-onnx/blob/master/pascal-api-examples/tts/piper-playback.pas) |

The clip size estimates use duration times bitrate divided by eight. For 30 six-second lines, three minutes at 32 kbps is about 720 KB before packaging. A text script can stay editable regardless of playback choice. The game remains in control of scene timing and existing dialogue remains on NVDA. Estimated work is 30–60 minutes to inventory remaining eligible scenes, 45–90 minutes to implement and verify the first clip-based scene and menu controls, and 5–12 minutes per additional cue once verified. A separately installed neural voice backend needs a separate 2–4 hour integration and performance estimate after the backend is selected. Numbers are engineering estimates, with in-game mixing and actual production recording still unverified. Voice implementation awaits the user's choice.
