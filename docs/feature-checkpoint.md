## Verification and player handoff

Before production integration, qualify a matched offline NW.js/plugin host with no game launch, exact existing loader/order and stock/custom lifecycle fixtures. The core uses actual producers with finite text/record counts, owned snapshots, stale-generation cancellation and nonblocking output. Match test fixtures to the installed build, keep source-bearing inputs outside Git and report simulated APIs. A mock DOM is enough to check registration order; it cannot establish the runtime's safe hook window. If a remaining critical fact needs live capture, name the exact producer and unresolved question and why offline evidence cannot answer. No capture is authorized by this investigation; an authorized capture must be persistent until user stop or game exit.

Measure equivalent mod-off/on cold boot, initial load, map/boat/scene transitions, cutscene and battle entry, busy field, puzzle resets, fast battle cues and repeated action bursts. Record combined work per frame/cycle, episode totals, sustained frequency and queue backlog. Report tail/worst latency from native state/input through usable route, cue or speech; snapshot age, cancellation delay, memory and recovery from helper loss. The 25 ms cumulative mod-caused application-lag threshold is a blocker, not a per-call budget. Set tighter budgets justified by accepted native timing. Throttled fixtures validate functional bounds; actual game responsiveness remains a final confirmation item.

After the complete implementation, offline checks and verified local deployment, provide the player a short ordered test script covering title/load and output recovery; menus and battle timing as soon as available; Salt Caverns correct/wrong order and reset; then world travel, ordinary unlocks, hidden areas and the optional cave when progression permits. Each test gives an action, expected speech/cue, common failure and the earliest natural point to try it. Keep engine/technical verification separate from player usability confirmation.
