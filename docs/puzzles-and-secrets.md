# Puzzles and secrets: offline audit

This is a build 26578620 engineering register. It identifies mechanics and source locations and contains some spoilers. It is not a walkthrough. Locators are `MapNNN.json` and event/page IDs under the installed `package.nw/data`; no game files are copied. “Confirmed” means the mechanic was traced in the shipped data, not played. **Ordered crystals and secret-cave stealth are the two confirmed complex families found in this pass.** This is not an exhaustive count of the game's puzzles.

## Salt Caverns guide

- On a settled walking map in Salt Caverns, **Shift+G** starts or reviews the guide. Before reading a wall clue it selects a nearby active clue. Request directions, then use the native action button at the wall. After the game presents the color order, **Shift+G** reads it back. Use **Objects** to find crystals and the reset. A crystal gains its color label after the game presents it. After a passage change, use **Exits** and current directions to check the route.
- **Ctrl+G** stops guidance, including while the map's dialogue is open. On an Xbox-style pad, press and release **View**, then press **LB** to start or review, or **RB** to stop. Change the keyboard chords in **Keyboard bindings** and the buttons in **Controller bindings**. The default bumpers continue to go to the game outside mod mode. [Field controls](navigation.md#destination-controls-in-the-development-build)
- The guide remembers the clue, revealed colors, witnessed lights and last relevant outcome for the current map scene. It identifies the native automatic reset separately from using the reset control. On re-entry or reload, reread the wall clue if needed. The reported lights describe observed interactions and resets. The first crystal's native event can re-evaluate its progress condition after a child reset has dimmed the lights. Directions continue to use the settled terrain and current blockers.

## Secret cave contact and recovery

Map 196 events 4–7, 12–15 and 17–18 use stock event touch on their active patrol pages. The first room's patrols call common event 102 when either the player or the mech attempts to enter the other's occupied tile. The stock `Game_Event.checkEventTriggerTouch` checks the attempted target against the player's logical tile. From the player side, `Game_Player.checkEventTriggerTouch` uses the custom `startMapEvent` and `findEventsAt` at original `MapScene.js` bytes 109478 and 110176. Those functions account for an event's optional rectangle. The follower collision override at byte 108393 leaves the player tile as the collision source. The map adds a red light to patrols and uses a dark tint. The first room's patrol commands contain tile movement, waits and turns, with no facing-based detection found. Camera position, lighting and movement speed still affect what a player can perceive or react to.

The first room's checkpoint is a floor interaction at event 21. It changes the checkpoint light, plays a cue, presents a message and later requests an autosave. Common event 102 switches patrols to an inactive page during capture, plays native feedback, presents the warning, then transfers via interstitial map 198. Its conditional destinations return to map 196 before or after the first checkpoint, or to either checkpoint on map 200. The common event restores native saving and HUD behavior after the recovery sequence. Re-enter only after the native field readiness gate. Never use internal checkpoint numbers as user-facing progress.

Map 199 events 22 and 24 start forced patrol routes and move the other start trigger. Map 200 events 5, 10 and 19 change enemy routes through distraction interactions. Map 201 uses separate chase triggers and forced movement. All of these need active-page and route ownership evidence before timed directions. Native autonomous movement uses `Game_Event.updateSelfMovement` and `Game_Character.updateRoutineMove`. Camera proximity, route wait counters, skip-on-block and forced routes affect when commands run. Stock `Scene_Map.updateMain` updates the map before player movement on a simulation update. The renderer may present a different number of frames. A patrol position or sprite facing alone cannot prove a safe crossing window.

The bounded world fixture checked the native failed-step path from both sides, suppressed contact while the interpreter owns the map and while the caught page is active, and proved that standing on the checkpoint tile starts its native event. It also retained all 120,972 existing collision comparisons. [Field and fixture procedure](navigation.md#offline-evidence-and-limits)

### Cave review and the warning sign

On an Xbox-style controller, press and release **View**, then press **LB** to review or **RB** to stop in an eligible field or dialogue context. - At the main entrance, the guide selects the warning sign. Request directions, follow the steps, then use the native action button at the sign. The sign route is confined to the southeast approach in Map 196. The pathfinder uses current tile and event collision. The **Objects** category includes the floor checkpoints and distraction crystals. The guide remembers a checkpoint message when the game shows it. After an active guide witnesses capture and confirms the actual landing, the next review identifies the return.
- Use native movement for the patrol rooms. The review describes a rendered instant and can age while spoken. Directions beyond the warning-sign approach use the timed preview below.

[The cave adapter](../src/world/puzzles/cave.js) uses Eli's current `Game_Event.getMapSprite` and its indexed character identity at original bytes 99512 and 108306 in `EliMZ_Book.js`. The adapter requires that attached sprite's viewport transform, texture, visibility and alpha after rendering. It conservatively excludes a frame whose footprint overlaps an upper tile or overpass. It uses the same tilemap reads and upper-layer classification as stock `Tilemap._addSpot`. This is a guard against reporting covered patrols. Partial or uncertain presentation can be omitted. Full lighting, GPU compositing and in-game speech latency remain gameplay checks.

Map 200 events 5, 10 and 19 supply the distraction routes. Event 19 page 2 supplies the return routes. In Map 201, events 4, 9, 11, 13, 24, 26, 27, 28 and 29 issue the chase routes. Stock `Game_Interpreter.command205` passes the authored route object to `Game_Character.forceMoveRoute`, which owns the object until the route ends or is replaced. The adapter checks the visible patrol and exact route owner. If a resumed save contains a copied route, the guide can still report its bearing. It waits for a verified route owner before naming the motion.

Checkpoint review comes from the fully presented native message on Map 196 event 21 or Map 200 events 6 and 15. Capture comes from the rendered message at common event 102 command 26, identified by the native message interpreter and exact list identity. Recovery uses the actual branch endpoints at command indices 33, 37, 41 and 45. The pending record contains only the expected map and tile, keyed by the native map instance. Pending recovery skips Map 198. A new transfer scene must be restored, rendered, settled and standing at the matching tile before the guide records recovery. If the player has moved before the first eligible sample, recovery remains unconfirmed.

The warning-sign worker request confines every step to columns 6–22 and rows 38–51, including the sign's final interaction approach. Repeating skippable routes can drift along their entire row or column. The adapter proves separation for those axes and uses the full extent for balanced non-skippable loops. Forced or unfamiliar routes disable this approach. The same predicate runs on worker delivery. Player movement, page changes, resource entry and transfers retire pending output. Other patrol movement between the key press and rendering is expected and the guide uses the new positions.

The installed-method fixtures verified off-screen, unready, covered and inactive patrol rejection, distraction/return/chase route ownership, and cancellation at player movement and event entry. ### Timed crossing previews

In the four patrol rooms, select a destination and request directions with the usual keyboard binding or controller trigger. The preview gives up to three steps in one direction. It ends at the first native floor event and labels that arrival. A short or unconfirmed opening produces a brief status. The regular warning-sign directions still apply in the entrance approach. The player moves through the native controls and can request another preview from the next standing tile.

The field adapter copies a bounded route phase, logical tile, interpolated position and current camera for each known mobile patrol. Native scene, movement, refresh, save and render checks govern admission. A live parallel event, scripted scroll or unfamiliar actor keeps timing unavailable. `Game_Map.updateEvents` supplies event order, and stock `Scene_Map.updateMain` updates map events before player movement. `Game_CharacterBase.moveStraight` reserves the destination when it accepts a move, then `updateMove` interpolates the displayed position. `Game_Event.updateSelfMovement` supplies the camera-range and stop-counter conditions. `Game_Character.updateRoutineMove`, `processRouteEnd` and `advanceMoveRouteIndex` supply waits, blocked and skippable steps, forced route return and repeat. The four cave maps are non-looping and have no overworld speed marker. The installed `MapScene` player speed wrapper at original byte 117350 uses stock speed here. `SceneManager.updateFrameCount` counts simulation updates for expiry.

The route worker starts from the first leg of the static route toward the selected destination, then checks starts over the next 60 simulation updates against live patrol movement, current collision and native camera scrolling. A prefix needs at least 45 checked start updates. It also checks one player-step duration after arrival when no native event takes over. The model stops at an unsupported native change, such as a switch command in a distraction route. A result needs at least 30 checked start updates remaining when returned to the renderer. Native frame expiry, player movement and protected phase entry close pending speech admission. The preview's checked interval applies to its original sample. Provider playback age and timely live movement cues still require evidence.

`tests/world.test.cjs` compared 912 updates against the installed native methods in memory. It covered blocked movement on each skip policy, near-screen movement, camera scrolling, forced routes, jump interpolation, and native contact. A real Map 196 crossing was replayed at four start delays inside its confirmed interval. After 35 native updates the same starting tile and destination produced no preview. Another case ended exactly at the floor checkpoint. The packaged worker completed this crossing in about 78 ms cold and 26 ms warm under the resource cap. Updating occupancy only when a logical tile changed reduced the same fixture's warm result from about 46 ms. The hidden matching NW fixture measured 0.7 ms for the synthetic timed command through worker enqueue and verified the returned speech record. These fixture results leave full-game cumulative lag, audible latency, alternative paths around a closed lane and live crossing/chase cues open. ## Finish the audit before implementation closes

1. Classify actual player reachability: follow active page priority, switches, variables, self switches, inventory and vehicle conditions; distinguish real progression, optional paths, duplicate map states and developer content. Compare all direct transfers plus common-event/plugin/script transfers against progression and quest data. A map ID in a transfer is not an unlocked route.
2. Sweep event commands and runtime readers for ordered branches, fail/reset, repeating patrol/forced move routes, timed controls, layer changes, touch triggers, tiles and blockers. Trace `MapScene` and `Tyruswoo` state effects and review baked visual cues. Keep unexplained candidates pending instead of declaring them inapplicable. One/two ordinary unlocks stay in Objects. Ask about a genuinely puzzle-like mechanic with fewer than two complex steps before adding a guide.
3. Record each actual puzzle as a finite player task: accessible clue and interaction, expected native state, safe route or native movement, failure/reset, completion, replay and what data proves each one. Use extracted native logic with real fixtures and the production adapter before final gameplay. Put clues and current state within reach of the player; any explicit assistance that exposes undisplayed solutions requires separate approval. Navigation labels may use reliable developer names under the standing exception; treasure/collectable labels give type only.
